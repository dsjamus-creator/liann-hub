# Hub session design and rollout gate

The hub verifies the email code through its same-origin Cloudflare Worker. The Worker receives the Supabase refresh token, encrypts it with the separate `SESSION_KEY`, and sets a host-only `__Host-liann-refresh` cookie with `HttpOnly`, `Secure` and `SameSite=Strict`. Page JavaScript receives only an access token and keeps it in memory. A reload calls `POST /session/refresh`; sign-out calls `POST /session/logout`, which requests Supabase `scope=local`, then clears the cookie. The Worker requires a matching `Origin` and rejects cross-site Fetch Metadata on all three POST endpoints. Responses have `Cache-Control: no-store`.

The sealed cookie also contains a random session identifier. The page sends that identifier on refresh and sign-out after sign-in, so an older tab cannot rotate or revoke a different account's newer cookie. Sign-in tells other open hub tabs to discard their in-memory tokens and account data, and clears the previous comic-reader cookie. A tab reloaded after the change can acquire the current browser session through the cookie. Concurrent sign-ins or refreshes in different tabs can still race at the browser's cookie store; one tab may need to sign in again. The staging concurrency check should exercise that case.

At rollout, the old `liann-hub-session-v1` localStorage value is removed without importing its refresh token into page JavaScript. Existing users must enter a new email code. Implicit sign-in links that return token fragments are rejected; the fragment is removed before rendering, and the user is directed to the code. The Supabase email template should emphasize the code. Reading position and recent activity remain account-scoped local preferences, not authentication credentials.

An access JWT already issued or copied remains usable until its expiry after sign-out. This design reduces durable script access to the refresh token; it does not make an active script injection harmless. A compromised browser/device or copied cookie can still be abused. Keep the restrictive CSP and complete the independent XSS/session review. The browser regression suite covers two-account switching, delayed responses and logout timing.

## Release gate: Supabase Auth capacity

The Worker currently calls Supabase Auth with the publishable key. A read-only dashboard check of the **actual** `pinyin-tiles-live` identity project (`mznljakkdafbqmapqncd`) on 24 October 2026 found 30 verification requests per five minutes per IP, 150 token refreshes per five minutes per IP, 30 sign-up/sign-in requests per five minutes per IP, and IP address forwarding **disabled**. [Supabase's Auth rate-limit documentation](https://supabase.com/docs/guides/auth/rate-limits) also lists `/auth/v1/user` in the sign-in bucket. Proxied calls may be counted against shared Worker egress IPs, so a coordinated rollout or 500-adult login/reload/comic surge could hit 429 responses. Existing users must enter a new email code at rollout. **Do not merge or claim 500-user readiness until the capacity design, edge abuse controls, and a bounded production-shaped staging surge test are recorded.**

The recommended scale design to evaluate is Supabase's opt-in `Sb-Forwarded-For` support, taking a validated `CF-Connecting-IP` from Cloudflare. Supabase requires a server-only `sb_secret` key for this; the publishable key will not activate the forwarding behavior. Such a key [bypasses RLS](https://supabase.com/docs/guides/getting-started/api-keys), so adding it requires a director risk decision. The Worker code now has a dormant `AUTH_IP_FORWARDING` switch, defaulting to `"0"`, and an optional `AUTH_SECRET_KEY` binding. If approved, create a dedicated secret key for this Worker, add it through the Actions secret, opt the project in and flip the switch in a reviewed PR. The code pins the exact `mznljakkdafbqmapqncd.supabase.co` Auth origin and forwards only a parsed Cloudflare visitor IP; it does not call the Data API with the secret. Never return or log the key.

The first draft used [Cloudflare Workers Rate Limiting bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/), but an isolated deployed probe allowed 48 of 48 fixed-key requests through a 10/minute binding. The revised draft uses 32 SQLite Durable Objects with 60-second counters keyed by an HMAC of the validated actor and `SESSION_KEY`. Verification has limits of 600/minute/IP and 10/minute/email; refresh has 600/minute/IP and 10/minute/sealed session ID; logout has 5/minute/sealed session ID. A shared-network user's refresh traffic does not block another session's logout. Invalid or missing IPs and unavailable counters fail closed with 503. Exceeding a limit returns a no-store 429 with the remaining `Retry-After` before contacting Auth. A limited session's logout must be retried after that window. Rotating `SESSION_KEY` resets counter identities as well as signing out existing sessions.

An access-gated **Worker and Durable Object only** staging probe on 24 October 2026 observed exact denials: 15 simultaneous requests to one email key yielded 10 allowed and 5 denied; eight to one logout-session key yielded 5 allowed and 3 denied. Five hundred simultaneous distinct synthetic session keys all returned 200, and 500 requests to one synthetic IP key returned 200 followed by 100 allowed and one 429. The final probe took 1.4 seconds for the distinct-key set and 0.9 seconds for the shared-IP set from one test client. Earlier one-object-per-actor prototypes produced 503s from Cloudflare internal/storage errors under 500 concurrent object creations; the 32-shard design removed those errors in the final probe. The stage Durable Object namespace and Worker were deleted after the test. This does **not** test Supabase, Render, R2, browser sessions or 500 signed-in adults. Cloudflare Durable Objects have [separate usage billing](https://developers.cloudflare.com/durable-objects/platform/pricing/). Record 401/429/5xx monitoring, a shared-network Auth surge, and an emergency rollback before merging.

The bounded, data-less Supabase preview-branch check on 24 October 2026 showed separate Auth verification buckets for two forwarded IPs: 30 invalid-code responses from one IP, 429 on its 31st and repeat, and an ordinary invalid-code response from the other IP using the same test client. The preview branch and its dedicated key were deleted after the test. The separate deployed Worker session test verified one synthetic sign-in, refresh rotation and logout, while the later Durable Object test above measured only the counter. None of these tests establishes token-refresh capacity, `/auth/v1/user` capacity or the 500-adult target. Use an approved production-shaped staging identity and backend environment for a bounded full-stack exercise.

## Deployment evidence

Before merging, verify `HUB_SESSION_KEY` exists as an Actions secret and that the deploy job actually uploads `SESSION_KEY` as a Cloudflare `secret_text` binding. A green test run with `Deploy skipped` is not a deployment. Record the merged commit, Worker version, date, current Auth settings, live code/reload/logout checks using synthetic accounts, and rollback point. Rollback restores the old JavaScript design, so it is an incident measure rather than a preferred steady state.
